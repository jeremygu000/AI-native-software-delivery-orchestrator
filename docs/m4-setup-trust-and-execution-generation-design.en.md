# M4.2 design draft: setup signer trust and execution generations

**Status: proposal for independent review; no signer, key registry, generation issuer, provider authorization or GLOBAL_READY production worker is implemented by this document.** The approved workspace-continuation design in `m4-workspace-continuation-design.en.md` remains the authority for setup-parent admission, one Git permit lineage and parent-to-child handoff. The accepted Ed25519 verifier at `8931825` proves only that an externally supplied key signed the exact setup decision in an exact artifact/execution-approval context. It neither authenticates the human named in `approvedBy` nor grants a mutation token.

## Trust principals and signed setup decisions

Separate four credentials and responsibilities: an authenticated **setup approver** decides whether the specific Git worktree operation is permitted; a **setup signing service** verifies that approval against the exact immutable plan artifact and execution approval before signing; an **execution supervisor/generation issuer** owns worker generations and their revocation; and an independent **recovery principal** verifies external quiescence and signs handoff/abandonment evidence. Builder/repair workers receive none of these signing or recovery credentials. A text `approvedBy`, a CLI argument, a file-store read and a recomputable fingerprint are never credentials. Signing service policy must bind the authenticated approver principal to the recorded decision, separately from the signer key ID; record the authentication method/policy version and audit the decision. This authentication workflow and its actual identity provider are **not yet chosen or implemented**.

The signing service verifies the complete `WorkspaceSetupApproval` against the approved artifact and execution approval, publishes the decision and `WorkspaceSetupAuthorization` as immutable paired records, and signs only `workspaceSetupAuthorizationMessage(setup, keyId)`. Its private Ed25519 key is unavailable to workers and to the unsigned record store. Publication must be idempotent for identical decision/signature/key ID; a different payload under the same ID fails closed. A signer response lost before durable publication is recoverable by comparing the exact signed bytes, never by accepting an unsigned record. The existing verifier remains a cryptographic primitive; a future admission API must also bind the verified decision to the _persisted_ run, registered scope, task, workspace, pinned repository/base commit and separately approved execution resources. It must not infer repository authority from an execution lease plan.

## Key registry, rotation and revocation policy

The future trust root is a separately administered, durable, versioned key registry, not a key embedded in either setup JSON document. Each key ID identifies exactly one Ed25519 public key and has an immutable registration identity plus effective state `ACTIVE | RETIRED | REVOKED`. Key-ID reuse or public-key substitution is forbidden. Registry updates use a restricted signer/trust-administrator principal, immutable audit entries and a monotonic registry revision. Provider admission/arming/permit transactions must read and validate the authoritative revision with a lock or equivalent serialization against registry updates, **as well as** their scope-row lock; a cached snapshot alone is insufficient. Define one consistent order (registry read lock → scope → run), with registry writers taking only the registry write lock, and never acquire the registry lock after the scope lock. PostgreSQL must not give the mutation runtime a key-admin role; a SQLite deployment needs a trust root and durable registry outside worker-controlled mutable files, or authenticated signed registry snapshots with rollback protection. An in-process `ReadonlyMap` alone is insufficient for production admission.

**Current-trust policy, not historical trust:** a _new_ setup-parent grant requires an `ACTIVE` signing key at grant time, regardless of whether the key was trusted at the record's `approvedAt`. A new arm or dedicated Git permit rechecks that the pinned authorization key remains `ACTIVE` and the exact signed decision has not been revoked. `RETIRED` permits verification for read-only historical audit but forbids new grants, arms and permits; `REVOKED` also forbids new effects and forces already admitted/armed parents into fail-closed recovery. A worker may never replace a pinned authorization with another signature to get around retirement/revocation; a new approval and new setup parent require a separately reviewed transition. If revocation races an in-flight Git permit, do not erase the permit or assume the external write stopped: mark/retain the parent uncertain, revoke its generation, then use independently proven quiescence and the recovery path. Exact read-only inspection of a committed handoff may report the original child, but must not relaunch an agent or create a new permit solely because an old key was once valid. Revocation/retirement during a handoff transaction is serialized/rechecked against the committed registry revision; a stale registry view rejects without releasing the parent.

Admission pins the setup approval fingerprint, full signed authorization digest, key ID, registry revision/policy version and separately approved execution-plan digest in durable phase evidence. Rotation registers a _new_ key ID and distributes its trusted public key before signing; retiring the old key blocks new authority from its existing signatures. Emergency revocation includes a durable decision/authorization denylist so a compromised signing key cannot mint ostensibly fresh accepted approvals before key-state propagation. The registry's administration, distribution and rollback protection must be designed and tested before any provider consumes the verifier; a signature creation timestamp or `approvedAt` supplied by the record cannot override current revocation.

## Generation issuance, revocation and supervisor containment

An execution generation is an opaque, issuer-allocated durable identity, **not** a worker-supplied random ID, PID, token or heartbeat. A restricted generation issuer registers exactly one generation for the exact `(scopeId, runId, taskId, attemptId, workspaceId, setup-parent claimId, worker/supervisor identity)` under scope serialization, pins the setup and execution approval digests, and persists `ISSUED` before allowing a worker to resume or arm. Retries may recover the same still-current generation by exact tuple; a competing worker or changed tuple cannot issue another live generation. Generation identifiers are unique and never reused; separate worker credentials attest which generation they present. Provider phase and permit checks read durable generation state under the scope lock and require `ISSUED` plus an ACTIVE bound run and exact owner/workspace. A signed generation certificate without current durable state is insufficient. The worker cannot issue, reassign or un-revoke itself.

The restricted supervisor/recovery route durably changes `ISSUED → REVOKED` under the same scope serialization as permit entry, before confirming any external stop; `REVOKED` is irreversible, and no new worker resume, arm or permit entry may use that generation. The scheduler must also refuse its activity retries/resumes; the provider and scheduler must share the authoritative revocation decision or fail closed on stale/unavailable state. Revoke-first is intentionally not proof of quiescence: an existing Git permit, spawned command or uncontrolled descendant may still write. A separately authenticated supervisor identifies the owned process/container/process group, prevents it and _all descendants_ from resuming or mutating, accounts for recorded permit lineage and provides durable termination evidence. If containment or a sink capable of rejecting stale generations at the actual write cannot be demonstrated, the parent stays blocking `HELD_UNCERTAIN` indefinitely. A new worker generation, wherever allowed, must not resurrect a revoked setup-parent permit lineage or replace the parent without the approved atomic handoff. PostgreSQL must preserve scope→run lock order; SQLite must serialize the same checks with its immediate transaction. A worker must not be able to rewrite registry/revocation rows directly, even if it can write its own ordinary progress records.

## Failure and concurrency obligations

| Event                                                                                | Required durable behavior                                                                                          |
| ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| Unsigned record, unknown/replaced key, stale registry, or untrusted signer principal | Reject setup admission without a claim, phase row or token allocation.                                             |
| Signing succeeds but immutable publication or response fails                         | Recover exact signed bytes and publication ID; never use an unsigned fallback.                                     |
| Key retires or is revoked before grant/arm/permit                                    | Reject new effect; keep any existing parent blocking until independent recovery.                                   |
| Key revocation races a live Git callback                                             | Retain exact permit and uncertainty; revoke generation and prove external quiescence before settlement or handoff. |
| Worker crashes after generation issuance but before setup grant                      | Generation stays identifiable; revoke it before reissue/abandonment; no setup claim may be fabricated from its ID. |
| Cancellation wins before arm or dedicated permit                                     | Provider rejects Git entry; revoke generation, then evidence-backed abandonment of the marked parent.              |
| Generation revoked during out-of-transaction Git inspection                          | Revocation remains durable; supervisor non-resumability proof must stay valid through the commit-time recheck.     |
| Issuer or registry unavailable during admission/arm/permit/handoff                   | Fail closed; no authority can be inferred from a cached signed record, heartbeat or old generation certificate.    |
| Revocation response lost after durable commit                                        | Exact retry observes `REVOKED`, never reactivates the generation.                                                  |

Before this design can authorize implementation, independently review the signing-service identity policy, key registry and denylist consistency model, generation issuer/supervisor privilege separation and actual external containment model. Require two-connection SQLite and real PostgreSQL tests for key-state and generation-state winner orders, startup/stale snapshot rejection, single-generation issuance, callback/revocation overlap and third-connection durable evidence; a real controlled Git/process fixture must demonstrate a revoked generation cannot resume after inspection. The approved parent phase/permit and handoff design still requires its separate atomicity and Git-attestation tests. No provider, CLI or worker currently uses these proposed operations. M4.2 stays OPEN, GLOBAL_READY production worker disabled and M4.3 not started.
