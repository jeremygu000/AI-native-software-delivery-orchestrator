# M4.2 design draft: setup signer trust and execution generations

**Status: proposal for independent review; no signer, key registry, generation issuer, provider authorization or GLOBAL_READY production worker is implemented by this document.** The approved workspace-continuation design in `m4-workspace-continuation-design.en.md` remains the authority for setup-parent admission, one Git permit lineage and parent-to-child handoff. The accepted Ed25519 verifier at `8931825` proves only that an externally supplied key signed the exact setup decision in an exact artifact/execution-approval context. It neither authenticates the human named in `approvedBy` nor grants a mutation token.

## Trust principals and signed setup decisions

Separate four credentials and responsibilities: an authenticated **setup approver** decides whether the specific Git worktree operation is permitted; a **setup signing service** verifies that approval against the exact immutable plan artifact and execution approval before signing; an **execution supervisor/generation issuer** owns worker generations and their revocation; and an independent **recovery principal** verifies external quiescence and signs handoff/abandonment evidence. Builder/repair workers receive none of these signing or recovery credentials. A text `approvedBy`, a CLI argument, a file-store read and a recomputable fingerprint are never credentials. Signing service policy must bind the authenticated approver principal to the recorded decision, separately from the signer key ID; record the authentication method/policy version and audit the decision. This authentication workflow and its actual identity provider are **not yet chosen or implemented**.

The signing service verifies the complete `WorkspaceSetupApproval` against the approved artifact and execution approval, publishes the decision and `WorkspaceSetupAuthorization` as immutable paired records, and signs only `workspaceSetupAuthorizationMessage(setup, keyId)`. Its private Ed25519 key is unavailable to workers and to the unsigned record store. Publication must be idempotent for identical decision/signature/key ID; a different payload under the same ID fails closed. A signer response lost before durable publication is recoverable by comparing the exact signed bytes, never by accepting an unsigned record. The existing verifier remains a cryptographic primitive; a future admission API must also bind the verified decision to the _persisted_ run, registered scope, task, workspace, pinned repository/base commit and separately approved execution resources. It must not infer repository authority from an execution lease plan.

## Key registry, rotation and revocation policy

The future trust root is a separately administered, durable, versioned **logical trust registry**, not a key embedded in either setup JSON document. One monotonic registry revision and one read/write serialization domain cover key registration and state, the exact setup decision/authorization denylist, and policy version. Each key ID identifies exactly one Ed25519 public key and has an immutable registration identity plus effective state `ACTIVE | RETIRED | REVOKED`. Key-ID reuse or public-key substitution is forbidden. The restricted trust administrator publishes key transitions **and** individual decision/authorization revocations under the same registry write serialization, advances the same revision and records immutable audit entries; a denylist in a separate non-atomic store or revision is insufficient. Reads of key, denylist and policy must be from one authoritative consistent revision, not a mixture of snapshots. Provider setup admission, arming, dedicated Git permit entry, handoff and child first-launch authorization take the trust-registry read serialization, validate the pinned key is currently `ACTIVE`, the exact decision **and** authorization are not denylisted, and the current policy permits the operation, then acquire scope and run locks in that order. Already-started child resume and permit entry use this **same** lock prefix with the narrower post-start rule stated below. Hold the read serialization through the authority transaction commit, so a concurrent registry writer either wins first and the operation rejects or commits afterward and triggers the revocation policy below; a cached snapshot alone is insufficient. Registry writers take **only** the registry write serialization, never scope or run, and no scope-locked operation may acquire the registry lock afterward. PostgreSQL must not give the mutation runtime a trust-admin role; a SQLite deployment needs a trust root and durable registry outside worker-controlled mutable files, or authenticated signed registry snapshots with rollback protection **and equivalent cross-store winner-order serialization**. An in-process `ReadonlyMap` alone is insufficient for production admission.

**Current-trust policy, not historical trust:** a _new_ setup-parent grant, arm, dedicated Git permit, `completeWorkspaceHandoff` **and first child agent launch** each require the pinned setup signing key still `ACTIVE`, the exact decision and authorization not denylisted, and current policy authorization under the single trust-registry serialization. Git success and independent quiescence are insufficient to mint the execution child after key retirement/revocation. `completeWorkspaceHandoff` closes the uncertain parent and grants a new child token only in the same trust-registry-read → scope → run transaction that rechecks current trust; retirement or revocation winning first leaves the parent blocking for evidence-backed abandonment. A committed handoff is not an agent launch: if the key ceases to be `ACTIVE` or the decision/authorization is denylisted before the first launch wins serialization, deny launch, retain the child as blocking authority, and use privileged independent recovery to revoke its generation, prove non-resumability and close it safely; never silently release it or retry with a substituted signature. The launch gate must persist an exact once-only child launch identity before permitting the external runner; a lost response cannot start a second runner. A launch authorization without independently confirmed actual start does not count as an already-started child for this policy: the trusted supervisor must recheck current trust and generation at the actual start boundary under the same registry serialization, and prevent a process from reaching any mutation sink until this check commits. If retirement/revocation wins between launch authorization and actual start, refuse the start; an uncertain start remains blocking until independently resolved. The scheduler and provider must use the same current revocation truth for subsequent resume and permits.

**After an independently confirmed child start, choose the conservative cascading policy for emergency `REVOKED` and exact decision/authorization revocation:** the descendant child remains durably linked to its setup key and authorization; revocation forbids its further scheduler resume and new mutation permits, revokes its execution generation, retains existing in-flight permits and makes its claim uncertain until independent containment/quiescence and privileged recovery. Registry writers still take only the registry lock; scheduler/permit entry enforces the committed revocation immediately under current-trust reads, while a restricted recovery actor performs scope-serialized child state/generation transitions. It must not rely on asynchronously updating a child row as its only fence. `RETIRED` is different: it blocks a not-yet-launched child and every new setup/handoff, but an already-started child may continue **only** under its separately approved execution authority, unrevoked generation and normal execution-phase checks; retirement grants no new authority from the old setup signature. For already-started child permits and scheduler resumes, the registry check therefore requires the pinned key **not `REVOKED`**, the exact decision/authorization not denylisted and the current execution policy valid; it does not demand the setup key stay `ACTIVE` after a confirmed start. This check still takes the same trust-registry read prefix before scope serialization through commit, so a revocation writer has a definite winner order. A worker may never replace a pinned authorization with another signature to get around retirement/revocation; a new approval and new setup parent require a separately reviewed transition. If revocation races an in-flight Git or child permit, do not erase the permit or assume the external write stopped: mark/retain uncertain authority, revoke its generation, then use independently proven quiescence and the recovery path. Read-only inspection of a committed handoff may report the original child but cannot relaunch it from historical trust.

Admission pins the setup approval fingerprint, full signed authorization digest, key ID, registry revision/policy version and separately approved execution-plan digest in durable phase evidence; the child also retains its immutable parent/key/decision/authorization linkage for revocation checks after handoff. Rotation registers a _new_ key ID and distributes its trusted public key before signing; retiring the old key blocks new setup authority from its existing signatures. The durable decision/authorization denylist shares the key registry's revision and lock so a compromised signing key cannot mint ostensibly fresh accepted approvals across a revocation race. The registry's administration, distribution and rollback protection must be designed and tested before any provider consumes the verifier; a signature creation timestamp or `approvedAt` supplied by the record cannot override current revocation.

## Generation issuance, revocation and supervisor containment

An execution generation is an opaque, issuer-allocated durable identity, **not** a worker-supplied random ID, PID, token or heartbeat. A restricted generation issuer registers exactly one generation for the exact `(scopeId, runId, taskId, attemptId, workspaceId, setup-parent claimId, worker/supervisor identity)` under scope serialization, pins the setup and execution approval digests, and persists `ISSUED` before allowing a worker to resume or arm. Retries may recover the same still-current generation by exact tuple; a competing worker or changed tuple cannot issue another live generation. Generation identifiers are unique and never reused; separate worker credentials attest which generation they present. Provider phase and permit checks read durable generation state under the scope lock and require `ISSUED` plus an ACTIVE bound run and exact owner/workspace. A signed generation certificate without current durable state is insufficient. The worker cannot issue, reassign or un-revoke itself.

The restricted supervisor/recovery route durably changes `ISSUED → REVOKED` under the same scope serialization as permit entry, before confirming any external stop; `REVOKED` is irreversible, and no new worker resume, arm or permit entry may use that generation. The scheduler must also refuse its activity retries/resumes; the provider and scheduler must share the authoritative revocation decision or fail closed on stale/unavailable state. Revoke-first is intentionally not proof of quiescence: an existing Git permit, spawned command or uncontrolled descendant may still write. A separately authenticated supervisor identifies the owned process/container/process group, prevents it and _all descendants_ from resuming or mutating, accounts for recorded permit lineage and provides durable termination evidence. If containment or a sink capable of rejecting stale generations at the actual write cannot be demonstrated, the parent **or already-started child** stays blocking and uncertain indefinitely. A new worker generation, wherever allowed, must not resurrect a revoked setup-parent permit lineage or replace the parent without the approved atomic handoff. Trust-aware operations prepend registry serialization; within the authority scope PostgreSQL preserves scope→run lock order and SQLite serializes the same scope/run checks with its immediate transaction. A worker must not be able to rewrite registry/revocation rows directly, even if it can write its own ordinary progress records.

## Failure and concurrency obligations

| Event                                                                                        | Required durable behavior                                                                                                                                                                             |
| -------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Unsigned record, unknown/replaced key, stale registry, or untrusted signer principal         | Reject setup admission without a claim, phase row or token allocation.                                                                                                                                |
| Signing succeeds but immutable publication or response fails                                 | Recover exact signed bytes and publication ID; never use an unsigned fallback.                                                                                                                        |
| Key retires or is revoked before grant/arm/permit                                            | Reject new effect; keep any existing parent blocking until independent recovery.                                                                                                                      |
| Decision/authorization denylist update races grant/arm/Git permit/handoff/first child launch | Same trust-registry revision and lock as key state: revocation winning first rejects with no new authority; authority winning first commits before revocation and follows descendant recovery policy. |
| Git completes and key RETIRES/REVOKES before handoff                                         | Handoff rejects under current trust, leaves parent uncertain/blocking; quiescence proof permits evidence-backed abandonment, never an execution child from historical trust.                          |
| Handoff commits and key RETIRES/REVOKES before first child launch                            | Launch rejects; child stays blocking without a runner, generation is revoked, and privileged independent recovery closes it only after proof; no replacement signature/relaunch.                      |
| Child has independently started; key RETIRES                                                 | Existing child may proceed under separate execution approval and unrevoked generation; no new setup/handoff/child from old signature.                                                                 |
| Child has independently started; key or decision/authorization is REVOKED                    | No future resume/permit; revoke child generation, preserve any live permit, retain uncertain child until independently proven stop and privileged recovery.                                           |
| Key revocation races a live Git callback                                                     | Retain exact permit and uncertainty; revoke generation and prove external quiescence before settlement or abandonment.                                                                                |
| Worker crashes after generation issuance but before setup grant                              | Generation stays identifiable; revoke it before reissue/abandonment; no setup claim may be fabricated from its ID.                                                                                    |
| Cancellation wins before arm or dedicated permit                                             | Provider rejects Git entry; revoke generation, then evidence-backed abandonment of the marked parent.                                                                                                 |
| Generation revoked during out-of-transaction Git inspection                                  | Revocation remains durable; supervisor non-resumability proof must stay valid through the commit-time recheck.                                                                                        |
| Issuer or registry unavailable during admission/arm/permit/handoff/child launch              | Fail closed; no authority can be inferred from a cached signed record, heartbeat or old generation certificate.                                                                                       |
| Revocation response lost after durable commit                                                | Exact retry observes `REVOKED`, never reactivates the generation.                                                                                                                                     |

Before this design can authorize implementation, independently review the signing-service identity policy, unified key/denylist/policy serialization, child revocation policy, generation issuer/supervisor privilege separation and actual external containment model. Require two-connection SQLite and real PostgreSQL tests for both key-state **and individual denylist** winner orders against grant/arm/Git permit/handoff/first launch, retired/revoked-key handoff and post-handoff prelaunch rejection, already-started child revocation, generation-state winner orders, startup/stale snapshot rejection, single-generation issuance, callback/revocation overlap and third-connection durable evidence; a real controlled Git/process fixture must demonstrate a revoked generation cannot resume after inspection. The approved parent phase/permit and handoff design still requires its separate atomicity and Git-attestation tests. No provider, CLI or worker currently uses these proposed operations. M4.2 stays OPEN, GLOBAL_READY production worker disabled and M4.3 not started.
