# Incremental review request: shared PostgreSQL deployment

Please review the shared-database increment against accepted baseline `db24cb592db0c593e23373e8c560672adb8b1f12` on `m4/postgres-durable-authority`. PostgreSQL 14–18 compatibility and explicit verified TLS are accepted. This increment makes shared database deployment practical while retaining the Forge schema authority boundary. The user requested a separate commit and push; independent acceptance remains pending.

## Intended scope

Database TEMP inherited from PUBLIC is allowed and reported as an observation. A deployment-owner connection creates a new empty Forge schema owned by `forge_owner`; that role receives no database CREATE in shared mode. The migration owner installs only in the prepared empty schema. Dedicated database-wide hardening remains an explicitly selected optional mode. No online Neon operation is authorized or performed by this increment.

Keep domain and engine provider-neutral. Preserve existing authority identity, protected mutation semantics, fencing, durability, workflow commands/patches, tracing, provider adapters and credential separation. Do not add a service, daemon, registry or new authority layer. Runtime's existing approved table DML is preserved; this stage does not convert every mutation into a new SECURITY DEFINER API.

## Changed areas

- `postgres-schema-deployment.ts` provides the PostgreSQL deployment boundary. It verifies the actual database-owner login, server major, schema name/absence and unprivileged Forge owner without effective database CREATE or outgoing membership. It creates only the named schema under the existing advisory lock, with PostgreSQL AUTHORIZATION. The database owner must already be able to SET ROLE to the schema owner; no role membership is granted by the tool.
- Fresh schema checks require the expected owner, owner-only ACL and no namespace-dependent objects. `pg_depend` detects more than tables: types, functions and sequences also prevent fresh adoption. Migration's `existing-empty` mode repeats these checks in its transaction and refuses missing schemas or owner database CREATE. Generic local install/upgrade remains separate.
- Runtime, trust, issuer, setup and recovery audits no longer reject TEMP. They continue to reject Forge-schema and pg_catalog CREATE, role escalation, prohibited relation/function privileges, PUBLIC grants, grant options and MAINTAIN. CREATE in an unrelated application/public schema is allowed. Existing restricted-role database CREATE/role-attribute restrictions remain.
- There is a measured reason for the function configuration change: a PG18 test reproduced a malicious `pg_temp.jsonb` domain being reached inside `forge_generation_write` with the old `search_path=pg_catalog`. The same test passes with explicit `pg_catalog, pg_temp`. The shared helper uses this safe startup path and audit catalog relations are qualified. A same-name temporary trust-registry table also cannot redirect mutation.
- The installer validates exact legacy or safe function configuration before setting the safe path, then verifies it again. Other path drift is rejected with rollback. Runtime refuses legacy paths until an operator reruns the installer; startup never performs the change. Historical migration definitions, checksum implementation, ledger versions and existing ledger rows are unchanged. This resembles existing ACL installation metadata, not a new workflow or schema migration.
- `neon-database-hardening.mjs apply DATABASE --shared-database SCHEMA` creates only the isolated schema. The dedicated mode retains its explicit acknowledgement, global ACL transaction and rollback behavior. Neon comparison preflight/bootstrap now requires the prepared empty schema, with no TEMP blocker. Both tools use shell-before-private-file TLS precedence. URLs remain query-free and TLS remains explicit verify-full.
- Deployment/observability instructions, `.env.local.example` and synchronized progress summaries explain these modes and the historical function upgrade. Product CLI PostgreSQL commands/provider picker remain later work; this stage uses the existing operator tool.

## Verification and evidence

The new shared-database regression runs the real operator as an actual non-superuser database-owner login. It retains PUBLIC TEMP and PUBLIC public-schema CREATE, compares database/public-schema ACLs before and after, preserves an unrelated public row, installs as `forge_owner` without database CREATE, reaches GLOBAL_READY and connects restricted clients. It rejects PUBLIC authority-table UPDATE, PUBLIC Forge-schema USAGE, runtime Forge-schema CREATE, invalid names, repeated preparation, wrong owner, missing schema and a pre-existing sequence. Dedicated-mode tests still verify acknowledgement, owner identity and rollback when an inherited TEMP grant survives.

The TEMP domain test failed before the explicit pg_temp-last correction and passes afterward. The migration configuration upgrade test compares the complete ledger before/after and refuses arbitrary unsafe function paths without repair. The existing authority suite now retains default PUBLIC TEMP throughout its fixture, exercising the accepted fencing, lock, schema, ACL and recovery contracts under that condition. PG16 passes five targeted changed-path regressions; the remaining 150 are intentionally excluded by the targeted filter, not reported as a full PG16 run.

`pnpm build` and full image-enabled `pnpm check` pass with the authority fixture on PG18: 1053 tests in 101 files, no skips. Coverage is 90.78% statements, 85.86% branches, 94.69% functions and 90.67% lines, above unchanged gates. Formatting, TypeScript, lint and `git diff --check` pass. Historical migration definitions and the checksum implementation are independently confirmed byte-for-byte unchanged from the accepted baseline. This stage performs no online Neon query or mutation, no live schema creation, no live GLOBAL_READY and no new provider comparison or Tempo acceptance.

## Limitations and review questions

Existing authority installations with the old function configuration require the migration-owner installer step before this worker version will accept them. Older workers that require the old exact setting will not start against the updated configuration, so installer/worker rollout must be coordinated. The schema-preparation tool does not grant its deployment owner SET ROLE capability or repair malformed default schema ACLs. Actual Neon provisioning/capability checks and traced E2E remain for the accepted live-deployment stage. New-schema bootstrap refuses all existing authorities; it does not take over or clean their state. The increment includes the new deployment module and this self-contained review request.

1. Does shared preparation mutate only the requested new schema, leave database/PUBLIC ACLs and other application data untouched, and avoid granting database CREATE to Forge?
2. Are database-owner identity, AUTHORIZATION prerequisites, schema ownership/emptiness and advisory-lock boundaries correct, including races and failed-install rollback?
3. Does allowing TEMP preserve schema/table/function/role authority isolation? Is explicit pg_temp-last configuration sufficient for the reproduced temporary-type attack and all existing SECURITY DEFINER functions?
4. Are legacy configuration upgrades restricted to the exact previously accepted path, with arbitrary drift rejected and migration evidence preserved?
5. Are restricted roles still unable to mutate protected authority surfaces or activate privileged roles, while unrelated schema CREATE remains harmless to Forge resolution?
6. Are dedicated hardening optional, explicit TLS/query-free URLs and credential isolation preserved, with local evidence distinguished from unperformed Neon deployment?
