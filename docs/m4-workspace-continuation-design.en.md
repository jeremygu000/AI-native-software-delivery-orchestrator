# M4.2 design draft: continuing after uncertain Git workspace creation

**Status: REVISED PROPOSAL FOR INDEPENDENT REVIEW; NOT IMPLEMENTED OR APPROVED.** The accepted workspace barrier at `d4ae9b8` deliberately leaves even successful Git creation `HELD_UNCERTAIN`. Existing reclaim closes that claim as `RELEASED`, not `ACTIVE`; initial admission cannot grant another claim for an already `STARTING` attempt. This design specifies a distinct, privileged phase handoff. It does not enable the production `GLOBAL_READY` worker or change the accepted provider behavior.

## Separate authority domains and durable phases

An initial **workspace-setup parent** is approved for exactly `{type:'repository'}` Git/worktree setup authority. A later **execution child** receives exactly the separately approved agent-execution lease plan. The child never inherits the parent's repository lease merely because Git needed it. If the agent must run repository-wide commands, the execution plan must independently and explicitly approve repository authority; otherwise its command permit is denied. Both plans and their approvals are immutable, bound to the same registered scope, run, task, attempt, agent and workspace, and rechecked by the provider. A missing or ambiguous plan/approval fails closed. This splits the setup authorization from the existing approved initial execution plan; implementation requires a new provider-neutral phase/plan contract and versioned PostgreSQL migration without editing v1–v4 checksums. Existing ordinary claims retain their current meaning.

The provider stores a one-to-one phase record keyed by parent and child IDs and serializes every transition with the scope lock (then the run lock when needed). The required phase states and allowed operations are:

| Phase                 | Ordinary `beginFencedMutation(parent, …)`                    | Dedicated workspace Git permit                                             | Ordinary release/reclaim                                    | Privileged handoff/abandonment                                   |
| --------------------- | ------------------------------------------------------------ | -------------------------------------------------------------------------- | ----------------------------------------------------------- | ---------------------------------------------------------------- |
| `INITIAL_ADMITTED`    | Reject; parent is setup-only from grant                      | Reject until marker commits                                                | Safe pre-Git close only through evidence-backed abandonment | Arm or abandon                                                   |
| `WORKSPACE_ARMED`     | Reject for **every** resource, even with repository coverage | Allow one exact workspace-create permit lineage only if run remains ACTIVE | Reject                                                      | Abandon with proof, not handoff                                  |
| `WORKSPACE_UNCERTAIN` | Reject                                                       | Reject new permits                                                         | Reject                                                      | Handoff or abandon after verified quiescence and settled permits |
| `HANDOFF_COMMITTED`   | Reject; parent is RELEASED                                   | Reject                                                                     | Parent already closed                                       | Exact replay of the same still-ACTIVE child only                 |
| `ABANDONED`           | Reject                                                       | Reject                                                                     | Parent already closed                                       | Never create a child                                             |

`armWorkspaceCreation` runs under the scope lock, re-reads the ACTIVE/current setup claim, bound ACTIVE run, approved workspace identity and setup plan, and commits `WORKSPACE_ARMED` **before any Git side effect**. Ordinary release/reclaim and permit acquisition re-read the same phase row under the same scope serialization: if an evidence-backed pre-Git abandonment wins first, arm fails; if arm wins first, ordinary release/reclaim fails. No composition convention or caller-supplied `purpose` flag may bypass this provider check. `beginWorkspaceCreationPermit` is a distinct provider operation with a non-forgeable single-use completion capability: under the scope lock it verifies `WORKSPACE_ARMED`, parent owner/token/version, repository setup lease, exact workspace and current unrevoked execution generation, bound ACTIVE run, and absence of a prior permit lineage, then durably records that lineage before returning the capability. Generic `beginFencedMutation` always rejects this parent, including while it is `INITIAL_ADMITTED`. Only the dedicated callback may use the workspace permit; a recovered permit has no completion secret. Even after an orphan is settled, no second workspace-create permit is minted for that parent: recovery must verify the actual result and hand off or abandon. A cancellation that wins before permit begin denies Git and leaves the marked parent for evidence-backed abandonment. Callback outcome or response ambiguity advances/retains `WORKSPACE_UNCERTAIN`; if recording uncertainty fails, the exact permit remains unresolved. No transition from uncertain back to armed or ACTIVE is permitted.

Abandonment is not a shortcut around handoff. It requires the **same independent, authenticated non-resumability proof**, scope serialization, confirmed uncertainty when Git may have started, and **zero unresolved parent permits**. Independently verified orphan permits are settled first through their separate exact-permit operation, never silently deleted by abandonment or handoff. Only then may the privileged operation close the parent and record `ABANDONED`; it cannot ever mint a child. Before Git starts, evidence must still prove the original generation was revoked and cannot start the armed operation later.

## Trusted quiescence and actual Git attestation

Only a **dedicated recovery service or operator principal**, separate from the builder/repair worker and its credentials, may issue a handoff/abandonment attestation. The provider authenticates this principal through a privileged recovery capability: PostgreSQL uses a separate restricted recovery role and signature verification; SQLite uses a recovery-service-held signing key absent from worker processes and verifies the signed canonical attestation before accepting a privileged operation. The worker can request recovery but cannot attest its own stop, supply an unsigned evidence string as proof, or invoke privileged phase completion through its ordinary mutation credentials. The recovery service persists an immutable, unique attestation ID and digest of canonical facts; the provider verifies signature, role/capability, digest, scope/phase identity and current revocation before accepting it. A compromised shared database or recovery signing key lies outside this trust boundary; deployment must keep recovery credentials separate from workers.

The recovery service first durably **revokes the original execution generation** in authority/scheduler state; every worker resume and every permit entry rejects that generation. An authenticated external execution supervisor must then confirm the owned process/container/process group has exited and that no uncontrolled descendant still holds a path to mutate the worktree. Use supervised containment or a sink capable of atomically rejecting stale generations; if any child process or raw writer cannot be accounted for, do not attest. Confirm Git has completed or stopped, account for every recorded parent permit (and settle each orphan separately only after proof), and keep the generation non-resumable for the entire Git inspection and handoff transaction. A quiet heartbeat, elapsed timeout, a single missing PID, Temporal activity disappearance or a successful callback response is insufficient. Stop/revocation evidence is durable and rechecked at commit; loss of the fence or stale evidence rejects and leaves the parent blocking.

The attestation binds `scopeId`, parent `claimId` and token, exact parent owner (`runId`, `taskId`, `attemptId`, `agentId`, `workspaceId`), workspace ID **and revision**, workspace permit lineage and observed permit IDs/states, original execution generation and worker/supervisor identity, revocation/termination evidence, and the approved setup and execution plan digests. It also contains the actual inspected Git state: canonical worktree path and canonical Git common-dir/repository identity, actual `HEAD` commit OID, separately approved pinned base commit OID, actual symbolic branch/ref and its OID, approved integration repository identity, and clean/expected initial worktree status (no agent has run yet). For a newly created workspace, require `HEAD` and its branch ref OID to equal the pinned base OID unless an independently approved setup operation explicitly specifies a different expected commit. Validate these against immutable approvals pinned **before** Git creation, not just a durable workspace JSON/path or self-reported branch name. If the workspace record was never saved, independent recovery must verify Git and durably reconcile the exact approved identity/revision before handoff; an unrecorded directory is never approval. Out-of-transaction inspection is valid only while the old generation is durably revoked and externally proven unable to restart; recheck the revocation and attestation identity in the commit transaction. Response-loss replay refers to the **same attestation ID and digest**, never a freshly sampled free-form equivalent.

## Atomic handoff and exact replay

Introduce privileged `completeWorkspaceHandoff` with a deterministic, domain-separated child claim ID derived from phase label, parent claim ID, run ID and attempt ID. Under one SQLite immediate transaction or PostgreSQL **scope-row FOR UPDATE, then run-row FOR UPDATE** transaction:

1. Require `GLOBAL_READY`, active scope, bound ACTIVE run, approved task and exact `STARTING` builder/repair attempt (including admitted repair work item). Re-read the immutable binding, separately approved setup and execution plans, `WORKSPACE_UNCERTAIN` phase, parent exact owner/token/version/canonical setup lease, parent `HELD_UNCERTAIN`, verified workspace record/revision, attestation ID/digest and current generation revocation. Require **no unresolved parent permit**; orphan settlement is a prior separate privileged operation. Validate the inspected actual Git identity and clean initial status against pinned approvals and the signed attestation. No worker/tool caller may forge these checks.
2. Check every other unresolved lease in the scope for conflicts with the **execution child's exact approved resources**, excluding only the exact parent being replaced. A conflict returns a stable blocked result with parent still uncertain and **no** child, token increment, attempt advancement or phase residue. A cancellation/terminalization that wins the scope lock first rejects handoff; later retry needs freshly validated proof.
3. In that same transaction record the attestation ID/digest, close parent as `RELEASED`, allocate one strictly higher scope-local token, insert child `ACTIVE` with **only execution-plan resources**, and commit the unique parent→child phase record. The attempt remains `STARTING` at its existing revision; no agent has run. Roll back all steps on failure. There is no visible parent-released/child-absent gap, and ordinary initial admission at `STARTING` cannot mint this child.

After commit, an exact retry matching parent, deterministic child, owner, **execution resources**, workspace identity/revision and **attestation ID/digest** returns the same still-ACTIVE child token and leases without repeating Git or allocating a token. Different evidence/identity/resources or an uncertain/released child rejects; parent cannot be reactivated. If commit fails, parent stays blocking. After successful handoff the old parent token starts no permit, while the child receives its required mutation context for subsequent controlled agent effects. Agent launch and final release are separate operations.

| Failure or competing event                                                                                          | Required result                                                                                                                                                                                              |
| ------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Marker commits, worker crashes **before Git permit begins**                                                         | Parent may remain ACTIVE but is setup-only and marked; ordinary permit/release/reclaim and handoff reject, no child. Revoke generation, attest that Git cannot start, then evidence-backed abandonment only. |
| Marker commits, cancellation wins **before Git permit begins**                                                      | Dedicated Git permit re-reads non-ACTIVE run and rejects. Parent remains marked and blocking; only independently proven abandonment can close it.                                                            |
| Git callback ends but permit response is lost                                                                       | Parent stays uncertain; recover exact permit and settle only after independent quiescence, then consider handoff.                                                                                            |
| Attestation absent/stale, actor alive, Git identity/status mismatch, workspace record missing, or permit unresolved | Reject handoff; retain parent and do not launch tools.                                                                                                                                                       |
| Another scope-local claim wins first                                                                                | Retain uncertain parent and return blockers; no child or token residue.                                                                                                                                      |
| Cancellation/terminalization wins first                                                                             | No child; retain parent. If handoff wins first, child remains blocking until independently stopped/settled; terminal state never auto-releases it.                                                           |
| Crash before/during handoff commit                                                                                  | All-or-nothing parent uncertain/no child; retry with verified current attestation.                                                                                                                           |
| Commit succeeds, response disappears                                                                                | Exact attestation ID/digest replay returns original child/higher token; do not recreate Git.                                                                                                                 |
| Crash after child grant, before agent start                                                                         | Child remains ACTIVE and blocks competitors; recovery proves whether an agent started before reuse or safe release.                                                                                          |
| Child runner/tool outcome unknown                                                                                   | Mark child uncertain, retain in-flight permits; never auto-release or mint another child.                                                                                                                    |
| Ordinary release/reclaim or abandonment races handoff                                                               | Marked parent rejects ordinary release/reclaim; privileged abandonment and handoff serialize on scope, only one commits.                                                                                     |

## Implementation boundary and required evidence

The existing legacy builder/repair services use local leases and legacy attempt transitions; they cannot be reused in `GLOBAL_READY`. A future global-only worker must recover the committed child, require its execution-phase mutation context, fence every later Git operation (including integration), implement global-safe attempt/impact/stop transitions, dynamic resource expansion and proven external-agent shutdown. Continue refusing production `GLOBAL_READY` startup until these are proven. M4.2 remains OPEN; M4.3 has not started.

Before approving implementation, require a shared two-connection SQLite/real PostgreSQL suite for every phase gate, ordinary-permit bypass attempt (repository parent requesting file/project/repository), one workspace-permit lineage, both marker/release and marker/cancellation winner orders, abandonment with unresolved permit, separated setup/child resources, exact attestation authentication and replay, Git state mismatch, failure-table rows, blocked zero residue and stale old-port callbacks. PostgreSQL additionally holds the scope row to demonstrate `pg_blocking_pids` for handoff vs claim, abandonment and cancellation/terminalization in both commit orders, with durable results inspected from a third connection. Use a real controlled Git workspace fixture and a supervisor/revocation fixture that can demonstrate a stopped generation cannot resume after out-of-transaction inspection. This is a design proposal, not proof that any of these contracts or tests already exist.
