# M4.2 design draft: continuing after uncertain Git workspace creation

**Status: PROPOSED FOR INDEPENDENT REVIEW; NOT IMPLEMENTED OR APPROVED.** The workspace creation barrier accepted at `d4ae9b8` intentionally leaves even a successful Git creation claim `HELD_UNCERTAIN`. The existing `reclaimUncertainMutation` closes that claim as `RELEASED`; it does not restore `ACTIVE` authority. The existing builder/repair admission allows a new claim only for a `PREPARING` attempt, whereas workspace creation follows an admission that has already moved the attempt to `STARTING`. Consequently neither retrying initial admission nor reclaiming and reusing the old token can start the agent. This draft defines the **next** operation; it does not enable a `GLOBAL_READY` production worker or revise the approved provider behavior.

## Safety rule and actors

The initial workspace claim (parent) and the subsequent agent-execution claim (child) are different immutable claims with different, increasing scope-local tokens. The child may be granted only after an **independent, privileged recovery actor** has established that the parent Git operation and any other external actor capable of writing under that parent cannot resume, and no parent callback is in flight. The recovery actor must also verify the actual Git worktree/branch and the durable approved workspace record. Seeing a matching workspace path, a successful callback response, a quiet heartbeat, or a missing worker is **not** proof of quiescence. No proof means the parent stays `HELD_UNCERTAIN` and blocks conflicting work indefinitely until explicit settlement.

The parent and child need not share a token; they must share the exact approved `scopeId`, run, task, attempt, agent, and workspace identity. For this initial continuation the child's resources must be **exactly** the canonical approved initial lease plan (including `{type:'repository'}` if workspace creation required it); resource expansion is a separate claim and is not part of this transition. A change in plan, binding, Git identity, or owner fails closed. Ordinary tool writes and repository commands use only the child token, passed as a required mutation context. The parent token must fail every new permit after transition.

## Proposed durable transition

Add a provider-neutral, privileged `completeWorkspaceHandoff` operation and a durable one-to-one parent→child phase record; implement it for SQLite and PostgreSQL with versioned PostgreSQL migration (do not edit v1–v4 migration checksums). Existing operations keep their present meaning for ordinary claims. A workspace-phase marker must identify the initial claim **before Git begins**; otherwise an ordinary `reclaimUncertainMutation` could release this parent in a separate transaction and bypass the atomic transition. Set the marker under the scope lock and require the Git callback to prove that marker and current parent authority when beginning its permit; otherwise a released parent must not start Git. Workspace-phase parents must be fenced from ordinary reclaim **and ordinary release**: only the atomic handoff or an explicit, evidence-backed **abandonment without continuation** may close them. That abandonment cannot later create a child from the abandoned parent. The handoff request contains the exact parent scope/claim/owner/token/version, independently verified quiescence evidence and its verifier identity, the approved run/task/attempt and workspace identity plus expected workspace revision, and a deterministic child claim ID derived from a domain-separated phase label, parent claim ID, run ID and attempt ID. The response contains the child token and leases, or a stable blocked result. The phase record links both immutable claim IDs, the workspace identity/revision, evidence and outcome; a unique parent key and unique child key prohibit a second child. The provider must not accept a caller-supplied free-form evidence string as an automatic proof of process termination: only a separately authorized recovery flow may attest the verified facts. The concrete attestation mechanism and its trusted principal are **review decisions before implementation**.

Under a single SQLite immediate transaction or PostgreSQL **scope-row FOR UPDATE, then run-row FOR UPDATE** transaction:

1. Require `GLOBAL_READY`, active scope and bound `ACTIVE` run; re-read the immutable alias/binding, approved task/plan, exact `STARTING` builder or repair attempt (including admitted repair work item), workspace-phase marker, workspace record and phase history. Check exact parent owner, token, version, canonical leases, `HELD_UNCERTAIN`, and the independent non-resumable quiescence attestation. An orphan permit must already have been settled using that independent evidence; any remaining parent permit rejects the handoff. Require a verified actual worktree, branch, pinned base commit and approved integration identity, not merely matching ref names or a JSON record. Keep Git inspection outside the database only if the attestation proves the stopped actor cannot restart between inspection and transaction commit. If Git created a worktree but saving the workspace record failed, the recovery flow must explicitly reconcile and durably record its verified identity before handoff; it cannot treat an unrecorded directory as approval.
2. Check **all other** unresolved leases in the scope for conflicts with the child's full resource set, excluding only this exact parent. If another run owns a conflicting resource, return blocked **without** releasing the parent, allocating a token, advancing the attempt, or writing a phase record. Cancellation or terminalization that wins the scope lock first likewise rejects transition without changing the parent. The recovery actor must re-evaluate attestation freshness before any later retry.
3. In that same transaction, append immutable handoff evidence, change the parent to `RELEASED`, allocate one strictly higher scope token, insert the child `ACTIVE` claim and all its leases, and commit the one-to-one phase record. The attempt stays `STARTING` with its existing revision: initial admission already advanced it, and no agent has started yet. Atomic commit leaves **no observable released-parent / absent-child window**. If any check or insert fails, roll back everything and leave the parent blocking. The ordinary first-claim API must never treat `STARTING` as authorization to mint this child.

The existing claim and phase history provide crash recovery: if the transaction commits but its response is lost, a retry with exactly the same parent, child ID, owner, resources, workspace record and evidence reads the phase record and returns the same **still-ACTIVE** child token and leases, without repeating Git creation or allocating another token. A different child/evidence/identity, or a child already uncertain/released, is rejected; it cannot resurrect the parent. If the recovery actor crashes before commit, the parent remains `HELD_UNCERTAIN`; if it crashes after commit but before agent launch, the child remains `ACTIVE` and blocks competitors until explicitly recovered, marked uncertain, or safely released with independent stop evidence. Launching an agent is a separate controlled step, never an implicit side effect inside the database transaction.

| Failure or competing event                                                                                              | Required result                                                                                                                                             |
| ----------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Git callback completed but permit end response lost                                                                     | Parent stays uncertain; recover exact permit and settle it only after independent quiescence, then consider handoff.                                        |
| Attestation missing, actor still alive, Git branch/base mismatch, missing workspace record, or parent permit unresolved | Reject handoff; retain parent and do not launch tools.                                                                                                      |
| Another scope-local claim wins first                                                                                    | Keep uncertain parent and return blockers; no child or token residue.                                                                                       |
| Cancellation/terminalization wins first                                                                                 | No new child; retain parent. If handoff wins first, the child remains blocking until safe stop/settlement; terminalization never releases it automatically. |
| Crash before or during handoff commit                                                                                   | All-or-nothing: parent uncertain, no child; retry requires fresh verified evidence.                                                                         |
| Commit succeeds, response disappears                                                                                    | Replay only the exact committed child with its original higher token; do not call Git create again.                                                         |
| Crash after child grant, before agent start                                                                             | Child remains active and blocks other writers; recovery must prove no actor started before release or reuse, never infer safety from elapsed time.          |
| Child runner or tool outcome unknown                                                                                    | Mark child uncertain while retaining in-flight permits; no automatic release or second child.                                                               |
| Ordinary release, reclaim or abandonment races the handoff                                                              | A marked workspace parent cannot use ordinary release or reclaim. Explicit abandonment and continuation serialize on the scope row; only one commits.       |

## Integration required before enabling a production worker

The current legacy builder/repair services create local leases and use legacy `claimBuilderStart`/`claimRepairStart`; `persistAttempt(STARTING/RUNNING)` is still a legacy writer gate after global cutover. They **cannot** be used unchanged. A future global-only execution path must recover the committed child admission, require its mutation context when constructing the Pi/tool runner, fence any Git operation that can write, and add scope-serialized global-safe attempt/impact transitions and a stop-confirmed release lifecycle. It must not expose the old uncertain claim to `createAgentTools`. Integration Git, dynamic resource expansion, external-agent shutdown proof, cancellation handling and terminal transitions all need their own controlled boundaries. Keep the existing production `GLOBAL_READY` startup rejection until these paths are proven; M4.2 remains OPEN and M4.3 has not started.

## Review and acceptance evidence to require

Before implementation, review (1) which independent actor can issue a non-resumable Git/process quiescence attestation, how its authority is authenticated, and how actual Git identity is pinned; (2) whether the initial plan can include repository scope without broadening unrelated tool writes, or needs a separate explicit Git claim; and (3) when the workspace-phase marker becomes durable, how ordinary reclamation is fenced, and how a verified but initially unrecorded worktree is reconciled. A shared two-connection SQLite/real PostgreSQL suite should cover every failure row above, exact parent/child tokens and state/version, no token or phase residue on rejection, stale old-port callbacks, and one child on lost-response retry. PostgreSQL must additionally hold the scope row to demonstrate `pg_blocking_pids` for handoff against competing claims, abandonment and cancellation/terminalization in both commit orders, and inspect results from a third connection. Test actual worktree identity with a controlled Git workspace fixture. Successful admission into an agent runner and final release require separate end-to-end proofs; documentation alone is not implementation acceptance.
